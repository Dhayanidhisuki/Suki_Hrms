01

What we are building, in one paragraph

A factory employs people. Those people arrive, work a shift, sometimes take leave, sometimes stay late, occasionally work a Sunday. At the end of every month somebody has to turn all of that into a number — what each person is owed — deduct the right taxes, produce a payslip, send a file to the bank, and file statutory returns with the government.

Today that happens in an old ERP and a lot of spreadsheets. We are replacing it. The HRMS is a machine that turns attendance events into money, correctly and provably. Everything else in the system — recruitment, documents, training, visitors — hangs off that spine.

If you remember one thing: the output is a payslip, and a payslip has to be right. Nobody complains about a slightly slow dashboard. Everybody complains when their salary is wrong.

02

The spine

Data moves in one direction. Learn this picture and most of the codebase becomes predictable — when you are handed a task, your first question is "where on the spine does this sit?"

Why this matters on day one

Almost every bug in a payroll system is a direction bug — something downstream quietly editing something upstream after the fact. If your change lets a user modify last month's attendance, you have broken payroll, even if every test passes.

03

Five layers

Every screen in this system belongs to exactly one of five layers. If you can't say which layer your task sits in, you don't understand the task yet.

04

Six ideas you need before you write code

These are the concepts that make otherwise strange-looking design decisions obvious. Read them once now; they will save you a week later.

Idea 1

Master vs transaction

A master is a setting — a shift, a leave type, a PF rate. A transaction is something that happened — a punch, a leave request, a payslip. Masters are edited by admins and are few. Transactions are created by events and are millions.

Master → Shift "General 08:30–17:30"
Transaction → Gopal worked General on 18 Aug
Idea 2

Never overwrite a rate

PF rates, tax slabs and salary structures change. If you overwrite the old value, re-running April's payroll in June produces June's numbers — which is wrong and, for statutory returns, illegal. Add a new row with an effective date instead.

UPDATE pf_rate SET pct = 13
INSERT pf_rate (pct, effectiveFrom)
Idea 3

Entitled vs earned

Every pay component exists twice. Entitled is what the contract says per month. Earned is what attendance actually justifies. A payslip must show both, and only the earned figure gets paid.

entitledBasic = 20,000
paidDays 26 of 30
earnedBasic = 17,333
Idea 4

One approval engine

Fifteen things need approval — leave, OT, transfer, salary revision, visitor passes. That is one engine with a type column, not fifteen sets of approvedBy columns. The chain is configured per type and per department, never hard-coded.

leave.approvedBy, ot.approvedBy…
ApprovalRequest(type, refId, step)
Idea 5

A closed month is closed

Once payroll is approved, attendance, leave, OT, permission and comp-off for that month all lock together. Reopening is a deliberate, audited act by an authorised user — not an edit button.

Open → Processing → Final →
Approved → FROZEN → Reopened*
Idea 6

Policy, not code

Grace minutes, OT factors, colour thresholds, incentive slabs — the client will change all of these. Every one is a row in a policy master that the engine reads. If changing a number needs a developer, the design is wrong.

if (lateMins > 10)
if (lateMins > policy.graceMins)
05

Flow A — a fingerprint becomes an attendance row

This runs thousands of times a day and is the foundation of everything downstream. A worker touches the scanner; nine steps later there is a row saying they worked 8 hours 43 minutes and were 2 minutes late.

Three traps

Missing punch. One punch, not two. Never guess the missing time — mark the day MP and let a human correct it through an audited screen.

Night shift. A shift starting 22:00 Monday ends 06:00 Tuesday. Which day does it belong to? Answer that in the shift policy, once, or you will have two wrong answers in different parts of the app.

Re-running sync. Syncing the same day twice must not create two attendance rows. Deduplicate on employee plus timestamp.

06

Flow B — overtime is a gate, not a subtraction

The most common beginner mistake in this module is writing ot = outTime - shiftEnd. That is wrong, and it will overpay people. Overtime is a series of gates; failing any one of them means zero OT, no matter how long somebody stayed.

07

Flow C — closing the month

This is the flow that makes the system trustworthy. A month moves through eight states, in order, and each transition is a deliberate human act. Nothing skips ahead.

Non-negotiable

Every write path in Attendance, Leave, Overtime, Permission and Comp-off must check the period status before saving. Build this into the foundation layer, not into each module — retrofitting it means auditing every endpoint you have already written.

08

Flow D — the payroll waterfall

Once the month is finalised, payroll runs the same waterfall for every employee. Each step consumes the one above it.

09

The build order

Eight stages. The order is set by dependency, not preference — each stage needs the one before it to exist. Day figures assume the whole team, not one person.

1

Configuration — the 60 masters

Every screen where an admin sets something up: departments, designations, shifts, holidays, leave types, PF and ESI rates, tax slabs, and the thirteen policy masters that drive attendance and overtime.

This is first because everything above it reads it, and because it is the only stage not blocked by the missing payroll formulas. It is also the cheapest way to put something real in front of the client.

People — employee record and lifecycle

The employee profile and its thirteen tabs, plus the lifecycle events that change it: confirmation, transfer, promotion, designation change, increment. Then letters, onboarding forms and separation.

The critical detail is versioning. A promotion does not edit the job record — it closes the old one and opens a new one with an effective date, so last year's payslip still reconciles.

The shape of the plan

The first genuinely usable release is the end of stage 5 — an organisation that can hire, manage, track attendance and pay people. That is roughly six to eight months with four developers. Stages 6 to 8 make it complete.

10

How to build one screen

Your first ticket will be a master screen. Here is the whole loop, start to finish, in this codebase. Once you have done it once, the other fifty-nine are the same shape.

Read what already exists

Open an existing master and copy its shape rather than inventing one. Departments is the simplest complete example, and the shared page component does most of the work.

// the two files worth reading first
src/app/masters/departments/page.tsx
src/components/SimpleMasterPage.tsx

Add the Prisma model

Follow the house pattern exactly: integer id, unique code, name, optional description, an active flag, soft delete, and timestamps. If the master holds a rate that can change, add effective dating too — that decision cannot be deferred.

model HolidayMaster {
  id            Int       @id @default(autoincrement())
  code          String    @unique @db.NVarChar(20)
  name          String    @db.NVarChar(100)
  holidayDate   DateTime
  holidayType   String    @db.NVarChar(30)
  isActive      Boolean   @default(true)
  deletedAt     DateTime?
  createdAt     DateTime  @default(now())
  updatedAt     DateTime  @updatedAt
}

Migrate

Never edit the database by hand. The migration file is the record of what changed and is what lets another developer — or the production server — reach the same state.

npx prisma migrate dev --name add_holiday_master
npx prisma generate

Write the API routes

Two files, five handlers. List and create in one, read, update and delete in the other. Deletes are soft — set deletedAt, never remove the row, because a payslip from March may still point at it.

src/app/api/masters/holidays/route.ts        // GET, POST
src/app/api/masters/holidays/[id]/route.ts   // GET, PUT, DELETE

Build the page

Point the shared component at your columns and fields. Resist adding a custom table — every master that looks slightly different is a maintenance cost for the next three years.

src/app/masters/holidays/page.tsx

Register it in the navigation

The sidebar is data, not markup. Add your screen to the tree and flip ready — the green dot and the progress counter update themselves.

// src/components/layout/navigation.ts
{ label: "Holiday Master", href: "/masters/holidays", ready: true }

Wire the permission

A screen nobody can be granted access to is not finished. Register the node in the permission model and check it in the API route, not only in the UI — hiding a button is not security.

Verify before you push

Types, lint, then your own eyes. Click through create, edit, delete and the empty state. Check it in dark mode and at phone width, because half the users are on the shop floor with a phone.

npx tsc --noEmit
npx eslint src/app/masters/holidays
npm run dev   // then actually use the screen
11

House rules

These come from reading the old ERP — 867 tables of hard-won lessons about what not to repeat.

Do

  • Store one row per employee per date, and let the database do date maths
  • Store pay components as rows, so a new allowance is data and not a deployment
  • Give every rate an effective-from date
  • Keep calculation in pure functions that take policy as an argument
  • Soft delete everything a payslip might reference
  • Record both the entitled and the earned figure
  • Check the period lock on every write
  • Put the reason on rejections and reopens — somebody will ask in eleven months

Don't

  • Create day1 … day31 columns — the old system did, and no date range can be queried
  • Add a column per pay component — the old salary table has 151 of them
  • Store leave balances as fixed columns per leave type
  • Cap anything at three or five with numbered columns (approver1, skill5)
  • Store a month as text next to a year as a number — it cannot be sorted
  • Write a threshold as a literal in an if
  • Let the attendance screen calculate salary its own way
  • Hard delete anything

Known unknowns — do not invent these

Half-day threshold · break deduction rule · night-shift date ownership · weekly-off source · minimum and maximum OT · earned-leave qualifying days · carry-forward limits · performance incentive basis · the payroll divisor · canteen and petrol rates.

If your task depends on one of these, stop and ask. A guessed threshold that reaches production becomes somebody's wrong salary, and it will be defended for months because it is already in the code.
