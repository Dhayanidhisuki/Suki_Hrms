## Requested change

Replace the current import choices:

- Basic Info
- Full Details
- Price Update Only

with one **Import Master Data** workflow matching the client's `Master List of Equipments and calibration monitoring` Excel format.

The intended workflow remains:

```text
Upload .xlsx
  -> parse and normalize headers
  -> validate every row
  -> show Create / Update / Rejected preview
  -> user confirms
  -> server revalidates accepted rows
  -> apply all writes in one Prisma transaction
```

The migration constraint is additive-only: no existing ERP columns or tables may be dropped, renamed, or destructively rewritten.

### Existing import behaviour

- Three explicit templates: `basic`, `full`, and `price`.
- Maximum file size: 5 MB.
- Maximum row count: 5,000.
- Frontend accepts `.xlsx`.
- Only the workbook's first worksheet is parsed.
- Headers are normalized using trim -> uppercase -> spaces to underscores.
- Preview performs row validation and does not write to the database.
- Confirmation revalidates the pending rows and writes in one Prisma transaction.
- Basic/Full import treats an existing `TOOL_OR_GAUGE_NO` as an update.
- Price import is update-only.
- Duplicate tool numbers within one file are rejected case-insensitively.
- Access requires an authenticated session and `canEditMaster` permission.

### Existing stock model

Stock is currently stored only as scalar totals on `GAUGEANDTOOLS`:

- `TOT_QTY`
- `QTY_IN`
- `QTY_OUT`
- `QTY_NEW`
- `QTY_IN_USE`

There is no `TOOLS_UNIT_STOCK` Prisma model or database migration in the repository.

### Existing unit representation

The application currently exposes these codes in `src/lib/toolCreate.ts`:

```text
All, Unit-1, Unit-2, Unit-3
```

They are code constants, not records from a modeled Unit table. The department lookup reads ERP table `DEPT` (`DEPT_NO`, `DEPT_NAME`) through raw SQL, but a department is not automatically equivalent to a company/unit. Therefore the proposed `TOOLS_UNIT_STOCK.UNIT_CODE` foreign key has no confirmed target yet.

## Proposed additive data model (draft only)

The central proposal is a new unit-wise stock table while retaining the existing master totals as compatibility mirrors.

```text
GAUGEANDTOOLS (existing, retained)
  REF_NO
  TOT_QTY / QTY_IN / QTY_OUT / QTY_NEW / QTY_IN_USE
       |
       | one-to-many
       v
TOOLS_UNIT_STOCK (new)
  REF_NO
  UNIT_CODE
  QTY_TOTAL
  QTY_IN
  QTY_OUT
  QTY_NEW
  QTY_IN_USE
  UNIQUE (REF_NO, UNIT_CODE)
```

No migration has been generated. Before drafting final Prisma types or SQL, the following must be decided:

- Whether `UNIT_CODE` references a real ERP Unit table, a new Tools-owned Unit table, `DEPT`, or an enumerated/check-constrained code.
- Whether calibration tracking values belong on each unit-stock record, in existing calibration history, or in a separate new table.
- Exact SQL Server types and lengths for any additive calibration fields.
- Source and ownership of opening unit quantities.

### Compatibility strategy

If approved, existing scalar quantity columns remain in place. Unit-aware issue/receive operations would update `TOOLS_UNIT_STOCK`, then recalculate and mirror aggregate totals into `GAUGEANDTOOLS` so existing screens and reports continue to operate.

The backfill must be insert-only into the new table. Existing master quantity values must not be overwritten during migration.

## Intended duplicate semantics

The proposed import identity is case-insensitive:

```text
(TOOL_OR_GAUGE_NO, USED_UNIT)
```

| Situation | Intended result |
|-----------|-----------------|
| Same equipment + same unit repeated in file | Reject later row |
| Same equipment + different units in file | Accept each unit row |
| Tool exists, unit row missing | Create `TOOLS_UNIT_STOCK` row |
| Tool and unit row both exist | Update unit-specific row |
| Tool does not exist | Create master once, then create unit row(s) |

Master fields are intended to come from the first occurrence of a tool number. Later rows for other units would affect only the unit-level record. This rule needs to be preserved explicitly in preview and confirmation logic.

## Validation requirements

Confirmed validation direction:

- `Equip No` required and at most 25 characters.
- `Used Unit` required.
- `Used Unit` must resolve to an approved unit master/code.
- Calibration frequency must be a non-negative integer when supplied.
- Validity days should be a non-negative integer if confirmed as numeric.
- Dates must accept real Excel date cells and supported date strings, then reject invalid values clearly.
- Same equipment/unit pair repeated in a file must be rejected.
- Maximum 5 MB and 5,000 rows remain unchanged.
- Preview must remain non-writing.
- Confirm must revalidate and apply atomically.

Potential correction: `Observed Error` sounds like a measurement and may require a decimal/string rather than the earlier generic numeric rule. Its type must be confirmed from real workbook values.

## Item-number analysis retained for separate work

Item-number generation is explicitly outside this import task.

Observed legacy patterns include prefixes such as `MP3`, `MS`, and `MP`, item/category codes such as `GST`, `DVC`, `PD`, `BG`, `HT`, and `W`, and numeric suffixes. Some legacy values contain additional suffix text or inconsistent category/name combinations.

No reliable name-to-code derivation rule was established. Auto-numbering should use maintained prefix/code lookups rather than guessing abbreviations from descriptions. It must be handled as a separate feature.

## Blocking decisions

Implementation must not start until at least decisions 1–3 are answered.

### 1. Description semantics — BLOCKING

Approximately 35% of source descriptions reportedly contain a short code while the rest contain expanded equipment names.

Decision required:

- Store the source value unchanged in `DES`, or
- Split short type code and expanded description into separate fields, or
- Apply a supplied client mapping/cleanup rule.

### 2. Make ownership — BLOCKING

`MAKE` currently exists only on `GAUGE_SERIAL_NO`, but the workbook has no serial number.

Decision required:

- Add a tool-level `MAKE`, or
- Place Make on a new unit-level record, or
- Obtain serial-level source data and retain the existing mapping.

### 3. Opening quantities — BLOCKING

The workbook has no quantity column. Unit-wise stock cannot be initialized truthfully without another source.

Decision required:

- Provide a separate opening-stock file,
- Add quantity columns to the source workbook,
- Perform a manual unit reconciliation after identity import, or
- Approve an explicit `Unassigned` backfill of existing totals until reconciliation.

Do not silently initialize stock to zero.

### 4. Unit master/FK target — BLOCKING FOR MIGRATION

Confirm what `Used Unit` references. Current code constants are not a foreign-key table, and ERP `DEPT` has not been confirmed as the correct business entity.

### 5. Calibration date source of truth

Confirm that the workbook's single `Calibration date` column is authoritative. Decide whether import creates `GAUGE_CONTROL_CARD` / `GAUGE_CONTROL_CARD_TRANS` history or stores imported opening calibration state separately.

### 6. Calibration field ownership and types

Confirm types and maximum lengths for:

- Validity days
- Observed error
- Calibration agency
- Calibration date
- Next calibration due

Also confirm whether these are tool-level, unit-level, or calibration-event-level attributes.
