## 2. Biometric Attendance module — built and verified end-to-end

**Schema:** `BiometricAttendanceImport` (113 columns — one wide row per employee per wage period, mirroring the customer's real legacy tables `HRMS_EMP_MON_ATT_DETAILS` / `_INTIME` / `_OUTTIME`, tagged `MANUAL`/`BIOMETRIC` via `fromWhere`) and `DailyAttendanceHistory` (snapshots superseded `DailyAttendance` values before every overwrite, from both the biometric pipeline and manual corrections — added mid-session after the user asked that old data never be silently lost on re-import).

**Pipeline** (`src/lib/biometricConversion.ts`): parses `HH.MM`-encoded punch times, derives status/working-minutes/late-minutes/OT-minutes per day, respects the existing frozen-month guard, and refreshes `MonthlyAttendanceSummary`. Rewritten twice during the session as requirements grew (see §4).

**UI** (`/workforce/attendance/biometric`): day viewer + bulk upload. The bulk upload format changed twice at the user's direction:
1. Started as three tabs pasting raw SSMS "Results to Text" grid output (one per legacy table shape) — the original design.
2. Changed to three downloadable CSV templates (Hours / In-Time / Out-Time), one per legacy shape.
3. Changed again to **one single template** — `EMP_ID, NAME, DATE, IN_TIME, OUT_TIME`, one row per employee per day — reshaped client-side into the wide per-source payload the API expects, grouped by calendar month. This is the shape that shipped.

**Real-data test**: extracted a 25-employee, Feb–Aug 2026 sample from the user's actual `attendance.rpt` legacy export (132,001 lines) and pushed it through the real import pipeline (not a synthetic fixture). In the process:

- **Found and fixed a genuine data-corruption bug in the legacy source**: `HRMS_EMP_MON_ATT_DETAILS` contains massive duplication — 10,712 raw rows collapse to 143 real (employee, wage-period) combinations, with one employee alone having 76 separate near-duplicate rows for one period. The original import logic treated later duplicate rows as authoritative and silently overwrote real punch data with near-empty fragments. Fixed by merging same-key rows (highest-populated-fields wins) before import; verified the corrected output against the real base record.
- **Found and fixed a casing bug** in the source data (`Apr-May` vs `Apr-may` etc.) that was splitting one logical wage period into duplicate landing rows.
- 25 employees created in KUN Aerospace via the real `POST /api/employees` handler (not raw SQL), each `oldEmployeeCode` mapped to a real legacy `EMP_ID`.
- Verified the full lifecycle on real data: create `PayrollRun` (`DRAFT`) → Finalize → **Freeze auto-triggered payroll recalculation** (`DRAFT` → `CALCULATED`, confirmed via the API response and a DB check) → Reopen (reason/user/timestamp recorded, status back to `OPEN`).

## 3. Real bugs found and fixed while testing live

1. **`/api/biometric` was never added to `src/proxy.ts`'s auth middleware** — in *two* separate places (the `config.matcher` array that decides whether the middleware runs at all, and a second independent `isApiRoute` string-match inside the middleware body that decides whether to actually attach `x-role-id`/`x-user-id`/`x-company-id`). The whole Biometric module had been returning 401s through the real browser since it was built; earlier verification only worked because it called route handlers directly, bypassing the middleware. Found via the user hitting genuine "Unauthorized" errors after signing back in — took three passes to find both gaps.
2. **Timezone display bug in Daily Attendance and Monthly Attendance** (`toLocaleTimeString()` on times that are stored as neutral wall-clock values via `setUTCHours`, not true UTC instants) — a 9:10 AM punch was displaying as 2:40 PM in the list view because the browser's local offset was being incorrectly re-applied. Pre-existing, unrelated to this session's new code, but directly in the way of verifying it; fixed both call sites.
3. **Collateral damage from environment debugging**: repeated `Stop-Process`/kill-all-node cleanups (needed to clear duplicate/orphaned background import scripts that were deadlocking on SQL Server locks) twice killed the user's own dev server session as a side effect, requiring restarts and a re-login. No data lost, but flagged so it doesn't repeat unnoticed.
4. The SQL Server backing this dev environment (`192.168.1.160:1433`, LAN-hosted) dropped connections mid-import at least twice (`P1001`). Added retry-with-backoff to the seed/import scripts rather than working around it silently; flagged to the user as a real production-risk pattern worth handling in the actual import route too, not just this session's scripts.

## 4. Shift, late-minutes, and overtime system

Grew directly out of reviewing the imported data: Late (min) and OT (min) columns weren't calculating, and OT that *was* showing was based on a flat, hardcoded 8-hour-day guess.

**What was built:**
- Discovered the app already had two dynamic, admin-editable masters — `ShiftMaster` (start/end/grace-minutes) and `OTPlan` (`applicableAfterMinutes`, `otRateMultiplier`, `maxOtHoursPerDay`) — that existed with full CRUD but were **never actually consulted by attendance conversion**. Wired both in rather than building new config surfaces.
- **Late-minutes calculation added** — didn't exist anywhere in the codebase before. `late = punch-in time − (shift start + grace minutes)`.
- **New `ShiftRotationPlan`/`ShiftRotationSlot` models** — an ordered weekly shift cycle anchored to a real calendar date (e.g. Shift 1 → Shift 2 → Shift 3 → back to Shift 1), with its own admin page (`/masters/shift-rotation-plans`, custom-built — the ordered-list editor doesn't fit the generic form component). The actual shift for any given day is computed from the anchor date, not stored per-day.
- **Employee shift assignment** (`Employee > Job Profile`): a `GENERAL`/`ROTATIONAL` choice — General uses a fixed `ShiftMaster`, Rotational uses a `ShiftRotationPlan`. Caught and fixed a step-config bug in the "Add Employee" wizard where the two new fields had been added to the form but never added to the wizard's step-grouping list, so they likely weren't rendering at all.
- Verified with a real 3-week rotation test (created, run, then fully cleaned up): shift correctly cycled week-to-week including an overnight shift (22:00–06:00), grace-minute subtraction was exact to the minute, and OT stayed correctly gated under the configured `OTPlan` threshold. Applied the corrected pipeline to the 5 real September-imported employees — all five now show real, hand-verified Late/OT figures instead of the flat placeholder.

**`ShiftPlan` removed entirely** (schema, table, API routes, admin page, nav entry, and every employee-form reference) at the user's explicit request, once `ShiftRotationPlan` made it redundant — "shift assignment should be General or Rotational only." One real pre-existing row (`Plan A`, one employee referencing it) was deleted along with the table.

**Leave Masters**: added a `defaultAnnualDays` field ("how many days can they take") with a `[−] [ N ] [+]` stepper — moved off the shared `SimpleMasterPage` component (used by 7 other unrelated masters) onto its own dedicated page rather than special-casing the shared one.

## 5. Verification methodology (unchanged convention)

1. `npx tsc --noEmit` and `eslint` after every schema/route/logic change.
2. Schema changes applied via targeted raw DDL from `prisma migrate diff --script`, not a blind `db push` — this DB carries two pre-existing unrelated drift items (bare unique indexes vs. named constraints on `Employee.userId` / `SalaryRevisionRequest.appliedRevisionId`) that break a full push; every migration this session applied only its own new statements and left that drift alone.
3. New backend logic verified by calling the real route handlers directly (via `tsx`, constructing `NextRequest` with real auth headers) against the real dev database — the same pattern the repo's own integration tests use — not mocks.
4. All throwaway verification scripts (`scripts/_*.mjs`/`.mts`) deleted after use; no diagnostic scripts left behind.
5. Test data (the 3-week rotation plan, its employee assignment, its attendance rows) fully cleaned up after verification. The 25 real imported employees and their September attendance are real, intentional data — not cleaned up.
