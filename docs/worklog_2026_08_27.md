## Part 1 — ERP data extraction path

### Why live credentials were declined

The client offered the ERP server's IP address and login so the credentials could be used to query `ERPDB_KUN_HRMS` directly. Before accepting, this was tested from the environment that would need to run the query:

- `curl` to an external host from the user's local shell returned `403` from a proxy — confirmed no general outbound network access.
- `npx prisma --version` failed to fetch its engine binary (`403` from `binaries.prisma.sh`) — confirmed the Prisma CLI cannot run in that environment either.
- No SQL client (`sqlcmd`, `mssql-cli`, `docker`, `psql`) or JS SQL driver (`mssql`, `tedious`, `knex`, `typeorm`, `sequelize`) is installed anywhere reachable.

Conclusion: a live connection is not currently feasible from either side, and separately, live production credentials shouldn't sit in a chat regardless. The client was asked not to send the IP or login, and a manual export path was proposed instead.

### Extraction package created — `scripts/erp-extract/`

Four files, targeting 26 master tables that carry **zero employee, payroll, attendance, or applicant data** — pure setup/configuration masters, safe to extract now without touching anything sensitive:

- **`README.md`** — explains two export methods (SSMS "Generate Scripts" wizard set to data-only, or the JSON export script below), and states explicitly that employee/payroll/attendance/applicant data is out of scope for this extract and belongs to a later, separately-scoped migration phase.
- **`tables.txt`** — the 26 target tables in 5 categories: Organization (5), Employee classification (5), Time and attendance (5), Payroll and statutory (7), Workflow and lookups (4).
- **`01-row-counts.sql`** — a fast, read-only `sys.partitions` row-count query. Sent to the client to run first; **response still pending**.
- **`02-export-json.sql`** — a `NOLOCK`-hinted `FOR JSON PATH` export per table, as a fallback if the SSMS wizard proves awkward.

Added it to `tables.txt`, `01-row-counts.sql`, and `02-export-json.sql` — the package now covers 26 tables, up from 25.

## Part 2 — Employee Details master field map

### Input

Client uploaded `Employee details master page brd old.docx` — 40 screenshots of the live ERP screen (`employeemaster.xthml` / `employeemaster1.xhtml`): the employee list page, the core create/edit form, and 14 sub-tabs (Personal, Contact, Job Profile, Salary, CTC, Education, Experience, Emergency Contact, Passport, Dependent, Assets, Skill Matrix, KYC, Activity).

### Work done

Every screenshot was read and every visible field cross-referenced against the current `Employee` model and its related tables (`PersonalDetails`, `JobInfo`, `SalaryStructure`, `EmployeeBankDetail`, `EmployeeDependent`, `EmployeeExperience`, `EmployeeEducation`, `EmployeeDocument`, `EmployeeAssetAllocation`). Output: **`docs/EMPLOYEE_MASTER_FIELD_MAP_2026-08-27.md`**, a section-by-section field table (ERP field → control type → proposed target → status: OK / GAP / NEW TABLE / DUP / FLAG → notes), delivered to the client and committed to `docs/`.

### Key findings

- **Job Profile tab is entirely unmodeled** — roughly 25 fields (bank/PF/ESI/OT/LTA/permission-related) have no home on `JobInfo` today.
- **Salary Details tab has ~35 individual pay components** against `SalaryStructure`'s 6 flat columns — confirms the plan (already implied by queuing `HRMS_SALARY_COMPONENT`/`HRMS_SALARY_LOGIC` for extraction) to model salary as components rather than more flat columns. Captured a real business rule directly off the screen: **PF Pay = BASIC + EDUCATION ALLOW + HEALTH ALLOW + LTA**.
- **Emergency Contact, Passport, Skill Matrix, and Activity** need new child tables; none exist today in a form that matches the ERP's repeating-grid structure.
- **Skill Matrix confirms the SKILL1–5 anti-pattern live** (`HRMS_EMP_SKILL_MATRIX`), and led to discovering `SKILL_NAME_DETAILS` (see Part 1).
- **Security flag**: Job Profile stores a plaintext "Official Password" field on the employee record — recommended excluding this from the new schema.
- Four items logged to the running contradiction table in `docs/REQUIREMENTS_DECISIONS.md`:
  1. The employee form's "Level" dropdown (L1–L7) conflicts with the agreed Org Structure decision that Level is a 5-tier organizational rank — same root issue as an earlier contradiction, now confirmed live in the UI.
  2. Five overlapping classification dropdowns on one employee (Category, Sub Category, Type, Grade Code, Class) — need plain-English definitions before any become schema fields.
  3. Statutory IDs (PAN, Aadhar, UAN, PF No, Driving License, Election/Ration card) are re-entered across three tabs with no single source of truth.
  4. CTC exists both as a pre-hire concept and as a mostly-empty post-hire Employee tab — likely redundant.

### Not decided yet

All four contradictions above, plus the open questions in the field-map document itself (Sub Category vs Class meaning, whether "Type" duplicates `EmployeeType`, whether two structured addresses are needed, whether CTC should be tracked post-hire at all, and confirmation on the "Official Password" field's real-world use). No Prisma model or field was added — this stays queued behind the client's answers, consistent with the "field map first, then model" workflow.
