### Navigation defined as data

Created `src/components/layout/navigation.ts` (593 lines).

- The entire tree is data, not markup. Screens are added, renamed or reordered in this one file.
- Exported `navigation` (the tree) and `allNavLeaves` (a flat list carrying each screen's module and group), used by the sidebar search and the placeholder screen.
- Each leaf carries `label`, `href`, an optional `short`, and an optional `ready` flag.
- `ready: true` marks screens that have a real page. It drives the green availability dot and the build-progress counter.

### Sidebar rewritten

Rewrote `src/components/layout/Sidebar.tsx` (312 lines) to render three levels.

- **Accordion behaviour** — one module expands at a time, and the module containing the current route opens automatically. With 203 items, allowing all 14 modules to expand simultaneously was not usable.
- **Module search** — a filter box above the tree flattens all 203 screens and matches on screen name, module name or group name. Each result shows its `Module · Group` path. This is the fastest route to a deeply nested report.
- **Availability dot** — a small accent dot marks screens that exist.
- **Build progress card** — a footer card showing `21/203` with a progress bar.
- **Collapsed mode retained** — icon-only rail; clicking a module expands the rail and opens that module.
- Replaced the previous static "Daily Meeting" placeholder card with the build-progress card.

### Placeholder route added

Created `src/app/[...slug]/page.tsx` (98 lines).

- A catch-all route so the ~182 unbuilt sidebar links resolve to a proper "this screen is not built yet" card rather than a 404.
- The card shows the screen's module, group, name, route and module icon, plus sibling screens in the same group for quick lateral navigation.
- Genuinely unknown routes still render a 404 state.
- Real pages take precedence over this catch-all, so no existing route is affected.

## Part 2 — Screen name shortening

Long BRD names were truncating in the 272px rail. **94 short names** were applied — 5 modules and 89 screens.

### Approach

`label` continues to hold the full BRD name and is used for page titles, breadcrumbs, search results and BRD traceability. A new optional `short` field is used **only** in the sidebar rail; both module and leaf rows render `short ?? label`, with the full name available as the hover tooltip.

### Naming rule

- Drop whatever the parent module or group already states — no "Report" inside Reports, no "Approval" inside Approvals, no "Deduction" inside Deductions.
- Keep standard HR abbreviations: PF, ESI, PT, TDS, LWF, OT, CTC.
- Never shorten to a term that is ambiguous on its own.

### Module renames

| Full name | Sidebar name |
|---|---|
| Learning & Development | Learning |
| Document Management | Documents |
| Approval Center | Approvals |
| Employee Self Service | Self Service |
| Administration | Admin |

### Result

Longest sidebar label reduced from **32 characters to 21**. No label truncates at the current rail width.

## Part 4 — Topic 1 answered: Organization Structure

Status moved to **PARTIAL**.

### Decisions recorded

- **O1** — Manufacturing company, structured department-wise.
- **O2** — A fixed five-tier position hierarchy applies organization-wide:

  | Level | Tier | Example designations |
  |---:|---|---|
  | 1 | Founder | Founder |
  | 2 | C-Suite | CEO, CTO, CFO |
  | 3 | Reporting authority / Department Head | HR Head, Production Head |
  | 4 | Mid-level | Team Leader, Supervisor |
  | 5 | Workforce (headcount base) | Operators, staff |

- **O3** — Level means organizational rank, not a pay band. The five levels are fixed and do not vary by department.
- **O4** — Employees are classified category-wise and designation-wise in addition to their level.
- **O5** — Headcount is reported department-wise and cumulative.

### Build impact assessed

Already supported, no change needed:

- `JobInfo` carries `departmentId`, `subDepartmentId`, `designationId`, `categoryId`, `gradeId`, `levelId` and `unitId`, and is versioned through `effectiveFrom` / `effectiveTo`, so transfers and promotions retain history.
- `Employee.reportingManagerId` is a self-referencing foreign key, so a named reporting chain is already possible.
- Department-wise cumulative headcount can be derived by grouping current `JobInfo` rows — no new model required.

Change required:

- **`Level` needs a numeric `rank` field (1-5, unique).** It currently stores only `code`, `name` and `description`, so levels cannot be ordered or rolled up. This blocks the organization chart and the headcount dashboard.
- `Designation` may need an optional `levelId`, pending confirmation of whether a designation is permanently tied to one level.
- No Company or Branch model exists; pending the single-entity question.

### Open questions raised (Q1.1 - Q1.10)

The blocking one is **Q1.7** — whether every employee has a named reporting manager or the manager is derived from level plus department. This determines the entire approval routing model, and retrofitting it later would mean re-tagging every employee.

Also outstanding from this topic: single or multiple legal entities, number of plants/units, whether Levels 1-2 belong to a department, the precise meaning of "cumulative", the employee category list, and what Grade now means given Level is organizational rank.

Noted for the client: Factories Act compliance forms (25, 15, 21, 22) are filed **per factory premises**, not per company, so the number of plants must be settled before compliance work begins.
