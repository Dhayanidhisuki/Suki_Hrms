## 3. Company-scoped RBAC — superadmin / company-admin

### 3.1 Requirement

The existing RBAC (`system-admin` / `hr-admin` / `hr-viewer`) was global/flat — no company scoping on `Role`, `Permission`, or `User` at all, despite `Company`/`Unit`/`Employee` already being multi-company. Requested structure:

- **Superadmin** — platform-level, not tied to any company. Creates `Company` records and bootstraps each company's first admin login.
- **Company Admin** — scoped to one company only. Creates further users/roles within that company; can define fully custom roles and toggle module (permission) access, confined to their own company.
- Permission **catalog** stays global (shared list of grantable actions); only the **grants** (which role has which permission) are company-scoped via `Role.companyId`.

### 3.2 Schema changes (`prisma/schema.prisma`)

- `Role`: added required `companyId Int` (FK → `Company`, `onDelete/onUpdate: NoAction`), replaced the global-unique `code` with `@@unique([companyId, code])`.
- `User`: added nullable `companyId Int?` and `isSuperAdmin Boolean @default(false)`; `roleId` made nullable (superadmin has neither `companyId` nor `roleId`). `email` kept **globally** unique — login is by email alone, no company selector, so cross-company duplicates would be ambiguous at login.
- `Company`: added back-relations `roles Role[]`, `users User[]`.
- `Employee.company` / `Employee.user` relations changed to `NoAction` — SQL Server rejects multiple cascade paths reaching the same table once `User.companyId` was added (`Company → User` direct, `Company → Role → User` indirect).

### 3.3 Migration

The DB user lacks `CREATE DATABASE` permission, so `prisma migrate dev`'s shadow-database step (`P3014`) doesn't work here. Used `prisma migrate diff --from-url <DATABASE_URL> --to-schema-datamodel prisma/schema.prisma --script` to generate SQL directly against the live DB (no shadow DB needed), reviewed it with the user before applying, saved it as `prisma/migrations/000006_add_company_scoped_rbac/migration.sql`, and applied via `prisma migrate deploy`.

Two pre-existing issues surfaced along the way (both unrelated to this change):
- Migration `000005_add_asset_allocation_details` was already applied to the DB but its `_prisma_migrations` tracking row was left in a failed state — resolved via `prisma migrate resolve --applied`.
- The generated diff re-proposed a plain `UNIQUE` constraint on `Employee.userId` that already exists as a **filtered** unique index (`WHERE userId IS NOT NULL`, from migration `000001`) — same known `prisma migrate diff` quirk already documented in migration `000002`'s notes; excluded from `000006` for the same reason (applying it would break correctness given multiple `NULL` `userId` rows).

Before migrating, three legacy rows were removed as they didn't satisfy the new NOT NULL `Role.companyId` and were confirmed non-functional test data: the `admin`/`viewer` `Role` rows (dated 2026-07-17, self-described "Skeleton admin role for RBAC demo") and the one `admin@suki.hrms` `User` row pointing at them, plus their 29 `RolePermission` grant rows.

### 3.4 Application code

- `src/lib/jwt.ts` — `TokenPayload` extended to `{ userId, isSuperAdmin, roleId?, roleCode?, companyId? }`.
- `src/app/api/auth/login/route.ts` — branches on `user.isSuperAdmin` to sign the right payload shape.
- `src/proxy.ts` — injects `x-is-superadmin` and (when present) `x-company-id` headers alongside the existing `x-user-id`/`x-role-id`/`x-role-code`; added `/superadmin/*`, `/api/superadmin/*`, and `/api/auth/me` to the protected-route matcher.
- `src/lib/rbac-superadmin.ts` (new) — `requireSuperAdmin()` guard, same pattern as `checkAdminPermission`/`checkMasterPermission`.
- `src/lib/companyScope.ts` (new) — `getCompanyId()`, reads `x-company-id` from the verified session only (never trusts client body/query), used by every `/api/admin/**` handler.
- `POST /api/auth/seed-superadmin` (new) — bootstraps the first superadmin; refuses once one already exists.
- `POST /api/superadmin/companies` / `[id]` (new, moved from `/api/masters/companies`) — Company is now the tenant root, editable by superadmin only. A read-only `GET /api/masters/companies` was kept (dropdown source for `Unit`'s `companyId` FK field).
- `POST /api/superadmin/companies/[id]/bootstrap-admin` (new) — upserts a company's 3 starter roles (`company-admin` [full access, renamed from the old global `system-admin`], `hr-admin`, `hr-viewer`) against the global permission catalog, then creates/repairs that company's first login.
- `src/app/api/auth/seed/route.ts` and `seed-user/route.ts` — retired (superseded by the above).
- `src/app/api/admin/users/**` and `roles/**` — every handler now scopes its `where`/`create` by `companyId` from the session header; `isLastActiveSystemAdmin` renamed `isLastActiveCompanyAdmin(companyId, ...)`.
- `src/app/api/auth/health/route.ts` — simplified to a read-only diagnostic (the old `?repair=1` path re-created the now-retired global `admin` role/user; removed).
- `src/app/api/auth/me/route.ts` (new) — lets the client know `isSuperAdmin`/`hasAdminAccess` for nav filtering.
- `src/components/layout/Sidebar.tsx` / `navigation.ts` — added a "Superadmin" nav section (Companies); "Administration" and "Superadmin" sections now hidden unless the logged-in user actually holds `admin.*` permissions / is superadmin (previously every section was shown to every logged-in user regardless of role).
- `src/app/superadmin/companies/page.tsx` (new, moved from `src/app/masters/companies/page.tsx`) — same DataTable/FormModal/ConfirmDialog pattern, plus a "Create / Reset" admin-login action per row.
