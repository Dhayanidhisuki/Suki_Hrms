## 2. Tier 1 — Time Office Phase 1 (Attendance + Leave)

**Scope:** Daily/Monthly Attendance + Leave — the true dependency root for Payroll (LOP days), skipping Comp-Off, standalone Permission requests, and biometric sync.

- **Schema:** `DailyAttendance`, `MonthlyAttendanceSummary` (OPEN/FINALIZED/FROZEN), `LeaveApplication`, `LeaveBalance` (migration `000007`).
- **API:** `src/app/api/workforce/attendance/{daily,monthly}/**`, `src/app/api/workforce/leave/**`.
- **Bug found and fixed during verification:** `POST /api/workforce/attendance/daily` returned `201` even when the month was already `FROZEN` — no route was checking `MonthlyAttendanceSummary.status`. Added `src/lib/attendanceFreeze.ts` (`checkMonthNotFrozen`) and wired it into all 4 write paths (daily POST, daily/[id] PUT, leave approve, leave cancel).
- **Pre-existing gap fixed proactively:** `GET /api/employees` had no company scoping at all — a real cross-tenant leak that the new Time Office employee-picker dropdowns would have surfaced. Added `getCompanyId()` scoping.
- **Verified:** LOP/OT calculation end-to-end, freeze correctly blocks writes after the fix, cross-tenant isolation.

## 3. Tier 2 — Payroll Processing Phase 1

**Scope:** gross → LOP-adjusted earnings → OT → PF/ESI/PT/TDS (flat-slab estimate) → net salary → approve → lock, with itemized payslips. Deferred: real Loan/Bonus integration (ad-hoc lines stand in), full annual TDS with regime/rebate/cess, bank transfer files, bulk PDF export.

- **Schema:** `PayrollRun`, `PayrollLine`, `PayrollLineComponent` (migration `000008`).
- **Core logic:** `src/lib/payrollCalculation.ts` — reads the employee's current `EmployeeSalaryRevision` + components (not the legacy `SalaryStructure` or unused `EmployeeCtc`), that period's `MonthlyAttendanceSummary`, and current `PfRate`/`EsiRate`/`ProfessionalTaxSlab`/`TDSSlab`. An employee with unfinalized/missing attendance is put on per-line `HOLD` rather than blocking the whole run.
- **Guard:** `src/lib/payrollGuard.ts` (`checkPayrollRunEditable`) — blocks recalculation/ad-hoc edits once `APPROVED`/`LOCKED`.
- **UI:** `/payroll/processing/salary` (run grid), `/payroll/outputs/payslip` (itemized payslip with ad-hoc add/remove).
- **Verified:** hand-calculated PF/ESI/PT/TDS/net matched exactly for a real test employee; HOLD correctly triggered for unfinalized attendance; ad-hoc add/remove updated net salary correctly and was blocked post-approval; Approve → Lock correctly rejected further edits (409, both UI and API); cross-tenant isolation (404 + empty list) confirmed via a disposable isolation-test company (created, tested, soft-deleted).

## 5. Tier 4 — Salary Revision & Arrear Phase 1

**Scope:** an employee-wise revision request with a single-approver workflow that, on approval, versions the employee's salary and auto-detects a retroactive effective date to generate a month-wise arrear, which is then pushed into Payroll as ad-hoc line items. Deferred: revision cycles/bulk upload, a configurable eligibility engine, multi-level approval, a separate arrear-approval stage, the full reports suite.

- **Schema:** `SalaryRevisionRequest`, `SalaryRevisionComponent`, `SalaryArrear`, `SalaryArrearMonth` (migration `000009`).
- **`src/lib/salaryRevisioning.ts`** (new) — the salary-versioning logic was extracted out of `POST /api/employees/[id]/salary` into a shared helper so both that route and the new approval flow use identical logic.
- **`src/lib/arrearCalculation.ts`** — retroactive detection walks every already-processed `PayrollRun` for the affected months, reads the *actual paid* `PayrollLine.grossEarnings` as "old gross" (not a re-derivation), computes gross/PF/ESI/net arrear per month.
- **`src/lib/arrearApply.ts`** — pushes a calculated arrear into a target `PayrollRun` as 3 ad-hoc line items (Salary Arrear / PF Arrear / ESI Arrear — 3 new `SalaryComponent` catalog rows seeded via `scripts/seed-arrear-components.mjs`), reusing Tier 2's ad-hoc mechanism.
- **UI:** `/payroll/processing/revision`, `/payroll/processing/arrears`.
- **Bug found and fixed:** `SalaryRevisionRequest.appliedRevisionId` used a plain Prisma `@unique` on a nullable column. SQL Server (unlike Postgres) only allows a single `NULL` under a plain unique constraint, and every non-approved request has `appliedRevisionId = NULL` — creating a second draft request failed with a unique-constraint violation. Fixed via migration `000010`, swapping in a **filtered** unique index (`WHERE appliedRevisionId IS NOT NULL`), the same fix already used for `Employee.userId` since migration `000001`.
- **Verified:** non-retroactive revision produced no arrear; retroactive revision produced an arrear matching hand-calculation exactly (`grossDifference=1200, pfArrear=144, esiArrear=9, netArrear=1047` on a ₹12,000→₹13,200 test case); recalculate reproduced identical figures and was blocked once `APPLIED`; apply correctly updated net salary and was blocked against an `APPROVED`/`LOCKED` run; Hold/Reject/Cancel all enforced mandatory reasons and left Employee Master/Payroll untouched; cross-tenant isolation confirmed.

## 6. Tier 5a — Bonus Management Phase 1

**Scope:** statutory-minimum bonus only (the BRD's own worked example: `min(basic, wage ceiling) × 12 × rate%`) against a configurable rate master, with the same single-approver workflow and Payroll-apply pattern as Tier 4. Deferred: the full allocable-surplus/Set-On-Set-Off variable bonus scheme, unit/category/performance-based rate determinants, true attendance-day-sum eligibility (a DOJ-vs-calculation-date proxy is used instead), bulk upload/export.

- **Schema:** `BonusRate` (versioned rate master, same shape as `PfRate`/`EsiRate`), `BonusRecord` (one row per employee per accounting year) (migration `000011`).
- **`src/lib/bonusCalculation.ts`** — eligibility (`ELIGIBLE`/`NOT_ELIGIBLE_WAGE`/`NOT_ELIGIBLE_SERVICE`), years-of-service, and bonus amount, batch-calculated per accounting year; recalculation skips `APPROVED`/`PROCESSED` records.
- **`src/lib/bonusApply.ts`** — pushes an approved bonus into a target `PayrollRun` as one ad-hoc `Bonus` earning line (new `SalaryComponent` row seeded via `scripts/seed-bonus-component.mjs`), reusing `checkPayrollRunEditable`.
- **UI:** `/payroll/processing/bonus`.
- **Verified:** three test employees (above wage ceiling, recently joined, genuinely eligible) all classified correctly with the right eligibility reason text; the eligible employee's bonus amount (₹3,998 on a ₹4,000 basic) matched hand-calculation exactly; approve → apply correctly added the ad-hoc earning and updated net salary; apply was correctly rejected both for an already-processed record and against a non-editable target run; Reject/Hold enforced mandatory reasons; cross-tenant isolation confirmed.

## 7. Scope decision — Gratuity split out as Tier 5b

The original plan bundled Bonus and Gratuity into one "Tier 5," but the BRD document itself treats them as two separate modules. Gratuity's core trigger — an employee's separation/exit date — has **no working entry point anywhere in the app**: a schema-only `ExitInterview` model exists (`exitDate`/`exitType`/`exitReason`) but zero API or UI reads or writes it. Rather than force it into the same pass, Gratuity was deliberately deferred as its own future tier (5b), starting with a minimal separation-entry flow. This was flagged to the user in the Tier 5a plan and accepted.

## 8. Cross-cutting issues hit repeatedly today

- **Windows file lock on the Prisma query engine DLL:** `npx prisma generate` fails with `EPERM` whenever the dev server is still running (it holds the DLL open). Fixed each time by stopping the preview server first, generating, then restarting.
- **Stale Turbopack cache after a dev-server restart:** a dynamic API route (`/api/payroll/runs/[id]/lines/[lineId]`) fell through to the catch-all page route and returned HTML instead of JSON. Fixed with `rm -rf .next` + restart — hit and fixed twice today (Tier 2 setup, Tier 5a verification).
- **Shell-unsafe `DATABASE_URL`:** the DB password contains characters (`` ` ``, `|`, `>`, `[`, `]`) that break both `bash` and PowerShell string interpolation when passed to `prisma migrate diff --from-url`. Every migration today used a small Node wrapper script (`spawnSync` with `DATABASE_URL` set via the child process's `env`, `--from-schema-datasource` reading it from `prisma/schema.prisma`'s own `env("DATABASE_URL")`) instead of a shell-interpolated CLI argument.
- **The `Employee_userId_key` spurious plain-unique-constraint line** that `prisma migrate diff` re-emits on *every* diff (documented since migration `000001`) was excluded from all 5 migrations generated today, per that established convention — and a second such line (`SalaryRevisionRequest_appliedRevisionId_key`) joined it after migration `000010`.
