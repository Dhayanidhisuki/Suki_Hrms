## Employee master import — segment-wise workbook

One workbook, one sheet per Employee-page tab, joined by `Employee Code`.
Agreed with the client in discussion, then built and smoke-tested the same
day. Full spec and decisions in
[EMPLOYEE_EXCEL_IMPORT_PLAN_2026-09-18.md](EMPLOYEE_EXCEL_IMPORT_PLAN_2026-09-18.md).

- **14 data sheets + Reference Lists.** Basic, Job Profile, Personal &
  Contact, CTC, Salary, Education, Experience, Passport, Dependents,
  Emergency Contacts, Benefits, Assets, Skills, KYC & Statutory. Activity is
  excluded — it is system-generated.
- **Mandatory: Basic, Job Profile, CTC, Salary, KYC & Statutory.** An
  employee missing a row on any of these is rejected whole. Everything else
  is optional, and the seven repeatable sheets take 0+ rows per employee.
- **Failure isolation.** A failing employee is skipped and every other
  employee still imports. A bad repeatable row (one education entry, say) is
  skipped and reported, never blocking the employee.
- **Dry run first.** Upload runs validation server-side and returns a
  per-employee, per-sheet report before anything is written.
- **Error workbook.** Failed employees come back in the same layout with
  `Status` and `Error` columns appended; HR fixes and re-uploads the same
  file, and the importer ignores those two columns on the way in.
- **Temp codes for new joiners.** HR writes `NEW-001` on Basic and repeats
  it across the sheets; the importer creates the employee, takes the
  generated code and maps it for the rest of the run. Both codes appear in
  the report.
- **Confirmation Date is a signal, not a write.** Filled → probation is
  dropped from the create payload so the employee lands CONFIRMED. Blank +
  probation period → PROBATION. Blank + a probation end date already in the
  past → rejected, because only the Confirmation approval workflow may
  fabricate that history. HR decides, not the system.
- **Status is locked to `active`.** No Status column at all — leave and
  separation belong to their own modules.
- Files: [employee-bulk-import.ts](../src/lib/employee-bulk-import.ts)
  (template builder, parser, `validateBatch()`, `buildErrorWorkbook()`),
  [bulk-upload/page.tsx](../src/app/employees/bulk-upload/page.tsx).

**Verified in the running app (logged in as KUN):** a 2-employee workbook
correctly blocked the one missing its KYC sheet; a fully-filled 14-sheet
workbook imported clean and was read back through every section API
(EMP185); a mandatory-sheets-only workbook also imported clean (EMP186),
confirming the optional sheets are genuinely optional.

Volume: 500–700 employees expected per file, capped at 1,000 per upload,
one transaction per employee, `maxDuration = 600`, no background queue.

- New **Permission** stat tile: approved hours for the month, the free

- New **Permission** summary panel: days with permission, approved hours,
  pending hours, free allowance, balance, excess.
- The old Attendance-panel row is relabelled **Permission (status)**, since
  it counts `DailyAttendance.status = 'Permission'`, not requests.
- Files: [overview/route.ts](../src/app/api/workforce/attendance/overview/route.ts),

### Monthly slab is now a hard cap

**Client decision, and a reversal of the 2026-09-07 BRD answer** — see Open
items. Previously an employee could apply for any number of hours and the
excess became LOP. Now
[permission/route.ts](../src/app/api/workforce/permission/route.ts) refuses
at apply time anything that would take the month past
`PermissionPolicy.freeHoursPerMonth`. Pending requests count against the
balance, so two requests that each fit cannot exceed it together.

Verified end-to-end against the real route on a 4 h slab:

| Request | Result |
|---|---|
| 3 h | 201 created |
| +2 h | 400 — "Only 1 h of the 4 h monthly permission allowance is left" |
| +1 h | 201 created (exactly fills the slab) |
| +0.5 h | 400 — "Monthly permission allowance of 4 h is already used up" |

Only 2 rows written, so nothing over the cap reaches an approver. The ESS
screen already surfaces the API error as a toast.

### Approved permission no longer charged as LOM

The gap the client raised: morning permission made the employee "late",
end-of-day permission made them "early out", and both were charged as LOM
even after approval. Approval changed nothing on the day.

`computeLomMinutes` ([attendanceCalc.ts:119](../src/lib/attendanceCalc.ts:119))
now takes `permissionExcusedMinutes`:

```
lateAfterGrace  = max(0, late − shiftGrace)
rawLom          = lateAfterGrace + earlyOut
afterPermission = max(0, rawLom − approvedPermissionMinutes)
lom             = dailyCap ? min(afterPermission, dailyCap) : afterPermission
```

- **Only `approved` excuses anything.** Pending leaves the LOM standing; it
  drops to zero on approval; rejection means it was right all along.
- **Capped at what was granted**, not the whole day — 1 h of permission
  against a 2 h late arrival excuses 60 minutes and leaves 60 chargeable, so
  a 15-minute request cannot wipe out a three-hour absence.
- **Stored `lateMinutes` is untouched.** HR still sees the employee arrived
  126 minutes late; only the charge goes to zero.
- New [permissionExcuse.ts](../src/lib/permissionExcuse.ts) loads approved
  minutes per employee per date in one query, wired into every place LOM is
  computed so no screen can disagree with payroll: Daily Attendance,
  Attendance Overview, Time Office Final, LOM approve and bulk-approve (the
  default approved figure no longer re-charges excused minutes), and the
  auto-deduct path in `payrollCalculation.ts`.

Verified live on EMP114, 15 Sep 2026 — 126 min late, 09:00 shift, 15 min
grace. Daily Attendance and Attendance Overview agreed at every step:

| Permission that day | Excused | LOM |
|---|---|---|
| none | 0 | 111 min |
| 1 h approved | 60 | 51 min |
| 2 h approved | 120 | 0 min |
| 2 h rejected | 0 | 111 min |

Test row deleted afterwards. Four unit tests added to
[attendance-calc.test.ts](../tests/unit/attendance-calc.test.ts) covering
the morning case, the early-going case, the partial excuse and
cap-after-excuse ordering — 15/15 pass.
