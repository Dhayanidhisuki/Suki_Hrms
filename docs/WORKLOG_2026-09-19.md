## Bulk leave entry — Leave Entry page

Agreed scope in discussion: HR files leave for many employees at once,
through the normal approval flow, with insufficient balance blocking the
row. Status is decided **by date**: leave starting before the current
calendar month is back-dated data entry and lands `approved`; anything from
this month onward lands `pending_manager`.

### Extracted the approval side-effects

[leave/finalizeApproval.ts](../src/lib/leave/finalizeApproval.ts). Approving
is not one update — it is balance ledger → `DailyAttendance` per date with
history → `refreshMonthlySummary` → comp-off ledger debit for `COMPOFF`. That
lived inline in the approve route. Any second implementation would drift and
silently desync balances from attendance, so `commitLeaveApproval()` now owns
it and the route is a thin wrapper. Guards (`checkFrozenMonths`,
`checkSufficientBalance`) are exposed separately so callers can dry-run them.

`checkSufficientBalance` takes an `alreadyReserved` argument — without it two
rows for one employee each pass against the stored balance and together
overdraw it.

### Import

[leave-bulk-import.ts](../src/lib/leave-bulk-import.ts) (template, parser,
status rule) and
[bulk-upload/route.ts](../src/app/api/workforce/leave/bulk-upload/route.ts)
(`mode=validate` writes nothing; `mode=import` re-runs the same checks and
commits). One sheet, one row per leave.

Three checks exist only because it is a batch: a **running balance tally**,
**overlap** against both the file and existing records, and **duplicate
detection** on exact employee+type+dates. Re-uploading the same file would
otherwise create duplicate rows that double-deduct once approved.

Fixed in passing: `companyId` was never set when creating a leave
application, despite the column existing for scoped queries.

UI on [entry/page.tsx](../src/app/workforce/leave/entry/page.tsx): a Bulk
Upload panel — template → file → Validate → Import, with an errors-first
results table showing each row's *"Will be: Approved/Pending"* before
committing. Import stays disabled until a dry run passes something.

Rows commit individually rather than in one transaction: a single late
failure should not roll back a 200-row load.

## Bulk approve / reject — Leave Approval page

Leave had only single-row approve/reject, while LOM and OT both had bulk
endpoints. Added
[bulk-approve](../src/app/api/workforce/leave/applications/bulk-approve/route.ts)
and
[bulk-reject](../src/app/api/workforce/leave/applications/bulk-reject/route.ts),
copying the `attendance/ot/bulk-approve` pattern. Each row dispatches by its
own stage, exactly as the single routes do, and approve goes through the
shared `commitLeaveApproval`.

- **Sequential, not parallel** — approving moves a shared balance, so two
  rows for one employee must be evaluated in order.
- **Skip, don't fail** — a frozen month, an overdrawn balance or a row the
  caller cannot action is skipped with a reason; the rest still go through.
- Reject never touches the ledger, per BRD §11.

UI: checkbox per row plus select-all with an indeterminate state (no change
needed to the shared `DataTable` — `Column.label` is already a `ReactNode`),
Approve/Reject Selected with a live count, and a **results panel** listing
each row's stage, outcome and reason. With per-row skipping, "42 of 50" in a
toast is useless without knowing which eight and why.

## Leave Approval queue was permanently empty

Reported as "approval action button is not there in admin". The buttons were
rendering; there were **no rows**, and there never have been.

The page requests `?status=pending`, and
[applications/route.ts](../src/app/api/workforce/leave/applications/route.ts)
passed that value straight to Prisma. `pending` is not a stored status — the
live stages are `pending_manager` and `pending_hr`:

```
status === 'pending'          : 0
status === 'pending_manager'  : 6
status === 'pending_hr'       : 3
```

Now treated as "either stage still awaiting a decision". The approval page is
the only caller of that param on this endpoint. The queue returns 9 rows.

That fix exposed a second problem: both stages now share one queue, but
`pending_manager` needs the employee's reporting manager and `pending_hr`
needs `workforce.leave.approve`. An admin selecting all 9 would have had 6
silently skipped. Added a **Stage column** — "With HR" / "With Manager" — so
it is visible before clicking, not afterwards in the results panel.
