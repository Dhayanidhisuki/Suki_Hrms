## 3. ESI/PF logic — explained, one small refactor, one no-op

The user asked a chain of questions about how ESI/PF are calculated and deducted, ending in a request to make the ESI eligibility check explicit.

- **Explained** (grounded in `src/lib/payrollCalculation.ts`, not assumption): ESI/PF deduction conditions, wage-basis (LOP-adjusted `grossEarnings`), how the amount both reduces `netSalary` and is itemized as its own `PayrollLineComponent`, and the current rates (ESI 0.75%/3.25%, PF 12%/12% — both read live from the `EsiRate`/`PfRate` masters, not hardcoded).
- **ESI condition rewrite:** the user described a two-condition rule ("total salary < 21000 → deduct; else if actual gross alone < 21000 → still deduct"). Traced through the math and confirmed this is **mathematically identical** to the existing single check (`grossEarnings ≤ ceiling` always implies the structured-salary check too, since LOP proration only ever reduces gross). The user asked for the explicit two-step version anyway, for code clarity — implemented in `payrollCalculation.ts` (lines ~168–181), verified via `npx tsc --noEmit` and a live recalculation of an existing payroll run (ESI stayed at ₹113, unchanged) confirming zero behavioral change.
- **PF employer-rate question:** user asserted the employer PF rate should be 13%, not the seeded 12%. Explained the actual EPF Act breakdown — 12% employer contribution into the employee's own PF+EPS account (matching the employee's 12%), plus 0.5% EDLI + 0.5% admin charges (employer-only overhead, never touches the employee's fund) = 13% total company cost. Also flagged that `PfRate`/`EsiRate` are **global, not company-scoped** (unlike `SalaryComponent`/`BonusRate`/`GratuityPolicy`, made company-scoped in prior sessions) — a change would apply platform-wide. Presented three options (edit in place, version it, or model EDLI/admin as separate new fields); **user chose to leave it as-is (12/12) — no change made.** Also reconfirmed a known gap: `employerContributionRate` on both `PfRate` and `EsiRate` is fetched but never used anywhere in payroll calculation — no employer-cost PF/ESI line exists today.

## 4. New feature request — leave day exclusion for weekly-offs/holidays (scoped, paused)

User asked: if a government holiday or weekly-off falls inside a leave application's date range, that day shouldn't count against the leave balance.

- **Investigated current state:** `numberOfDays` on a `LeaveApplication` is computed client-side as pure calendar days (`src/app/workforce/leave/entry/page.tsx`, `daysBetweenInclusive`) with zero exclusions, and the API (`POST /api/workforce/leave/applications`) trusts whatever the client sends — no server-side recomputation at all.
- **Confirmed the real blocker:** there is **no Holiday Calendar master and no weekly-off pattern configuration anywhere in the schema or codebase.** `DailyAttendance.status` has `WeeklyOff`/`Holiday` listed as possible free-string values in a comment, but nothing in the app ever writes them — it's a placeholder, not a working feature.
- Discussed whether weekly-off should be configured per-department or per-shift (the app already has `ShiftMaster`/`ShiftPlan` as the "different work pattern" concept, which is the more common real-world mechanism for rotational manufacturing shifts) — left open pending the user's answer.
- Proposed (and user agreed) a template-based bulk upload specifically for the **holiday calendar** (many rows/year — spreadsheet entry is more practical than a form), with weekly-off staying a simple masters-style config (few fields, no template needed).
- Drafted two short emails for the user to send: one to HR (raw weekly-off + holiday data), one narrower follow-up covering the still-open design questions (department vs. shift, Excel vs. CSV, replace-vs-merge on re-upload, optional/restricted holidays, whether to recompute existing applications).
- **No code, schema, or migration written for this** — user explicitly asked to hold until the data comes back from HR, expected to resume tomorrow.
