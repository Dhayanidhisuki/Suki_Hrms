# Suki HRMS — Employee Master Phase 1 Worklog

**Date:** 28 August 2026
**Modules:** Employees (Employee Master), Masters (Companies, Units), RBAC, Dev Environment
**Working branch:** `integration/hrms-complete`

## Objective

Implement Phase 1 of the Employee Master redesign per the client's BRD-driven spec (`SUKI_HRMS_EMPLOYEE_MASTER_IMPLEMENTATION_PROMPT.md`): collapse the old 13-page Employees > Profile submenu into a single Employee Master list plus a 15-tab employee profile, with 4 of those tabs (Basic Details, Personal Details, Contact Details, Job Profile) fully wired to real data. Then iterate the UI against live feedback through the rest of the day.

---

## Part 1 — Dev environment fixes

Before any feature work, the local dev server didn't run.

- `node_modules` had been installed on macOS — `node_modules/.bin` shims were POSIX-style (no `.cmd`), so `npm run dev` failed with `'next' is not recognized`. Fixed by pointing `.claude/launch.json` at `node node_modules/next/dist/bin/next dev` directly.
- `lightningcss`'s Windows native binary was missing (only the `darwin-arm64` build was present). Installed `lightningcss-win32-x64-msvc@1.32.0` and cleared the stale `.next` cache.
- Port 3000 was occupied by an unrelated project's server (`Suki_Ticketing`) at points during the day; used `autoPort` / re-attached configs rather than killing another project's process.

## Part 2 — Codebase audit

Read the full spec, the client's five `.rpt` reference dumps (`Organization.rpt`, `employee classificatin.rpt`, `payroll.rpt`, `Time and attendance.rpt`, `workflow.rpt`), and the BRD `.docx` (confirmed to be legacy-ERP screenshots whose fields already matched the spec's own field lists, so no separate re-derivation was needed).

Audited `prisma/schema.prisma`, the existing `/employees` pages/routes, `navigation.ts`, and `src/lib/rbac.ts`. Findings:

- Schema had reasonable bones (`Employee`, `PersonalDetails`, `JobInfo`, etc.) but was missing structured Contact Details, multi-emergency-contacts, Passport, unified KYC, Skill Matrix, an Activity/audit model, dynamic salary components, CTC, and an Employee↔User link.
- **Critical gap:** `/api/employees/*` had no working authorization at all (see Part 4).
- `Company` was explicitly marked "PENDING CLIENT CONFIRMATION" in the schema's own comments.

Four decisions were confirmed by the client before building: (1) add a full `Company` model, reuse the existing `Unit` model as Branch/Site/Plant, (2) scope employee-code uniqueness per company, (3) implement AES-256-GCM for future KYC encryption now, (4) local filesystem for file storage.

## Part 3 — Schema, migrations, RBAC, reference data

### Schema

Added `Company`, `EmployeeContactDetails`, `EmployeeEmergencyContact`, `EmployeePassport`, `EmployeeKyc`, `EmployeeSkill`, `EmployeeActivity`, `SalaryComponent`, `EmployeeSalaryRevision`, `EmployeeSalaryComponent`, `EmployeeCtc`. Extended `Employee` (company scoping, `userId` link, Basic Details fields), `PersonalDetails`, `JobInfo`, `Unit`.

### Migrations (all applied against the live `suki_hrms` SQL Server DB)

| Migration | What |
|---|---|
| `000000000000_baseline` | Baselines the pre-existing schema (no `prisma/migrations` history existed before today — the DB had been managed via raw `db push`) |
| `000001_employee_master_redesign` | The models above. `Employee.companyId` added nullable, backfilled against a seeded "KUNAERO" company row, then tightened to `NOT NULL` — all 3 existing employees preserved. `Employee.userId`'s `@unique` needed a **filtered** unique index (`WHERE userId IS NOT NULL`), not a plain constraint — SQL Server treats multiple `NULL`s as duplicate keys in a plain unique constraint. |
| `000002_move_nda_fitness_to_personal` | Moved `ndaDocument`/`fitnessCertificate` from `JobInfo` to `PersonalDetails` per live UI feedback (both were `false` everywhere — verified before moving, no data loss) |
| `000003_drop_contact_phone_fields` | Dropped `permanentPhone`/`presentPhone` from `EmployeeContactDetails`, consolidating to a single "Mobile No" per address block |

Two new SQL Server triggers added (`tr_EmployeeSalaryRevision_no_overlap`, `tr_EmployeeCtc_no_overlap`), matching the existing slab-table overlap-prevention pattern.

**Mechanical note for future migrations on this DB:** the DB user lacks `CREATE DATABASE` permission, so Prisma's shadow-DB-based `migrate dev` doesn't work here. The working pattern is `migrate diff --from-url ... --to-schema-datamodel` to generate SQL, hand-review it (Prisma's diff also re-proposes a plain `Employee_userId_key` unique constraint every time, which is wrong for the reason above and must be excluded), then apply statement-by-statement inside one Prisma interactive transaction (`$transaction`) so a mid-migration failure rolls back atomically — `prisma db execute --file` sends the whole script as one compiled T-SQL batch, which breaks when a later statement references a column added earlier in the same script (SQL Server compiles the batch before executing any of it).

### RBAC

Added `src/lib/rbac-employee.ts` (mirrors the existing `rbac-masters.ts` pattern) and seeded `employee.*` permission codes, granted to the admin role.

**Fixed a critical pre-existing bug while wiring this in:** `proxy.ts` only ever checked the `Authorization` header for API routes, never the session cookie — so every `/api/masters/*` and (once wired) `/api/employees/*` call from the app's own pages was silently 401ing, because those pages' `fetch()` calls never set that header (the browser sends the cookie automatically instead). Fixed by falling back to the cookie for API routes too. This had been broken for the entire masters module before today.

### Reference data seeded

`scripts/seed-company-and-org.mjs` (Company + 32 Departments + 100 Designations + Grades, from `Organization.rpt` / `employee classificatin.rpt`), `scripts/seed-salary-components.mjs` (35 components from `payroll.rpt`), `scripts/seed-employee-permissions.mjs`. All idempotent (upsert by code), verified by running twice.

## Part 4 — UI built

- **Employee Master list** (`src/app/employees/page.tsx`) — themed `DataTable`, search (now also matches Old Employee Code), pagination.
- **Add Employee** (`src/app/employees/new/page.tsx`) — originally one long stacked form; changed mid-day to a **tabbed** layout (Basic/Personal/Contact/Job Profile) per feedback, with all tab data held in one shared state object so nothing is lost switching tabs, and a single Create action at the end.
- **Employee Profile** (`src/app/employees/[id]/page.tsx`) — header + all 15 tabs in the strip; Basic/Personal/Contact/Job Profile fully wired (lazy-loaded per tab, atomic PUT saves, `EmployeeActivity` logging), the other 11 render a labelled "Coming in Phase 2" placeholder. Added unsaved-change protection: switching tabs with a dirty form prompts to discard, and a `beforeunload` guard covers page close/refresh.
- **Employee Activity** (`src/app/employees/activity/page.tsx`) — read-only global timeline, also searchable by Old Employee Code.
- **Companies master** (new) and **Units master** (updated to add the Company FK) under Masters.
- **Sidebar** — Employees > Profile collapsed to just "Employee Master" + "Employee Activity"; Lifecycle/Letters/Separation groups deliberately left untouched (out of scope).
- Shared field definitions extracted to `src/lib/employee-form-fields.ts` so Add and Edit never drift apart, per the spec's own requirement.

### Bug found while building: `Field.tsx` select coercion

The shared `Field` component's `<select>` always passed the raw DOM string to `onChange`, never coercing to match numeric option values (unlike the `number` input type, which did). This silently broke saving anything with a numeric-typed dropdown (`departmentId`, etc.) — confirmed it also affected the pre-existing Sub Departments and Units master forms, not just new Employee code. Fixed generally in `Field.tsx`: on change, look up the matching option and pass through its original typed value.

## Part 5 — Live feedback and iteration

Worked through several rounds of feedback while the app was open, each verified live in the browser afterward:

1. Add Employee form widened to fill the page (was capped at `max-w-5xl`).
2. Reporting Manager field added to Basic Details (had been missing entirely) — its dropdown shows both current and Old Employee Code, and both the Employee Master list search and the Employee Activity search were extended to match Old Employee Code too.
3. Title → dropdown (Mr/Mrs/Ms/Dr). Petrol Allowance moved from Basic Details to Job Profile. Daily Sheet Required and Induction Status removed from the UI (columns left in place, unused). NDA Document and Fitness Certificate moved from Basic Details to Personal Details — this one needed an actual schema migration (`000002`) since Personal Details is a different table.
4. Contact Details: "Present Same as Permanent" now copies the address **live in the browser** the moment it's checked (previously only synced silently server-side on save), and the Present fields grey out/disable while checked. Permanent/Present Phone and Mobile consolidated into one "Mobile No" field each (`000003` migration).
5. Guest Employee field removed from Basic Details. Mobile No capped at 10 digits (both `maxLength` on the input and a tightened regex server-side). Permanent/Present State converted from free text to a dropdown of all 32 Indian states (from `Organization.rpt`), added as a hardcoded option list (same pattern as Gender/Marital Status) rather than a new master table, since it's a fixed enumeration.

Each schema-affecting change (items 3 and 4) required regenerating the Prisma client and restarting the dev server — done once at the end of that batch rather than after each individual change, and only after checking with the user first, since the dev server was actively serving their browser and a mid-session restart briefly interrupts it.
