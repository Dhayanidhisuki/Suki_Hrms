## Announcements & circulars (gap G1) — built

- KUN MoM 23/June/2025 asked for policy updates and internal circulars on the
  employee portal. Nothing existed: `NoticeBoard.tsx` fetched `/api/notices`,
  which has no route, and sat on the HR dashboard rather than ESS.
- Migration `000066_announcements`: `Announcement` (DRAFT → PUBLISHED →
  ARCHIVED, category, priority, optional expiry) and `AnnouncementRead`
  (one receipt per employee, unique-indexed), plus the
  `platform.announcement.view` / `.admin` permissions and an
  `ANNOUNCEMENT_PUBLISHED` event and in-app template per company.
- HR authoring at `/admin/announcements`, employee view at
  `/ess/announcements`, both in the sidebar. Publishing fans out an in-app
  notification to every active employee with a login.
- Published items are frozen — editing a live circular would change what
  people already acknowledged, so it is archive-and-reissue. A published item
  archives; only an unpublished draft deletes.
- Read receipts are what make a policy circular auditable: the HR list shows
  "7 of 18 read".
- A login with no employee record (HR, admin) reads announcements but records
  no receipt — announcements are company-wide, and refusing HR the company's
  own circulars was wrong.
- In-app only, no email. The MoM asks for notifications *on the portal*; the
  channel flags are there if email is wanted later.

## Sidebar — HR users with an employee record

- Giving an HR user an employee record stripped every HR module from their
  sidebar. The branch tested `hasAdminAccess` (which means `admin.*` only —
  an HR Admin holds no such grant), so `hasEmployeeAccess && !hasAdminAccess`
  sent HR staff down the employee-only path. The file's own comment claimed
  the opposite behaviour.
- Added `hasHrAccess` (holds any permission) to `/api/auth/me` and branch on
  that. An HR user with an employee record now sees both sets — they are
  still someone who applies for leave and reads their own payslip.
- Both dashboards then render at once and collided: modules were keyed by
  `label`, and two are labelled "Dashboard". Keyed by `href` instead, which
  also fixes the two expanding together.

## Fixes found along the way

- `DataTable`'s `rowKey` prop was declared but never used, so every table
  keyed on `row.id` regardless.
- `POST /api/employees` accepts `jobProfile.userId` in its schema but passes
  it into `JobInfo.create`, which has no such column — any create that tries
  to link a login fails with `Unknown argument userId`. Worked around by
  creating first and then calling `PUT /api/employees/[id]/job-profile`,
  which handles it correctly. The create path is still broken.
- `useSearchParams` in a client page fails a production build without a
  Suspense boundary; dev renders on demand and hides it. Caught on the new
  ESS announcements page before it reached a build.
